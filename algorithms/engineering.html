Algorithm 04

工程算法

从三个具体问题开始：缓存满了删谁，扩容后哪些键搬家，一个名字是否值得去真实存储里查。先跟着状态变化走，再看省下的成本和必须接受的限制。

LRU：容量满了，淘汰最久没有使用的条目

缓存是为了重复读取时少做一次慢操作，但内存有限。LRU（Least Recently Used，最近最少使用）只记录“上次使用的先后顺序”：访问或更新过的键放到最近端，超出容量时从最久端淘汰。

输入：容量固定为 3，依次写入 A=1、B=2、C=3，再执行下面的操作。所有图都约定左端最久未用，右端最近使用；颜色只是辅助，图中同时写明动作。

操作返回 / 淘汰操作后的键顺序（左 → 右）
put A=1、B=2、C=3无淘汰A, B, C
get A返回 1B, C, A
put D=4淘汰 BC, A, D
get B未命中C, A, D
put C=30更新已有键A, D, C

为什么这样维护就够了？每次命中或写入都把这个键移到右端，其余键的相对顺序不变，所以最左端始终是最久没被使用的键。未命中没有访问到缓存条目，顺序也不应改变。这里把写入已有键也算一次使用。

Python 的 OrderedDict（有序字典）既能按键查值，也能移动条目。move_to_end 默认移到右端；popitem(last=False) 删除左端条目。可以对照 Python 官方文档阅读这两个操作。

from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self.capacity = capacity
        self.data = OrderedDict()

    def get(self, key, default=None):
        if key not in self.data:
            return default
        self.data.move_to_end(key)
        return self.data[key]

    def put(self, key, value):
        self.data[key] = value
        self.data.move_to_end(key)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)
cache = LRUCache(3)
for key, value in [("A", 1), ("B", 2), ("C", 3)]:
    cache.put(key, value)
print(cache.get("A"))        # 1
cache.put("D", 4)            # 淘汰 B
print(cache.get("B"))        # None（默认未命中值）
cache.put("C", 30)
print(list(cache.data.items()))
# [('A', 1), ('D', 4), ('C', 30)]

missing = object()          # 独立哨兵：区别“缺失”和“值是 None”
cache.put("E", None)
print(cache.get("E", missing) is None)     # True，确实缓存了 None
print(cache.get("Z", missing) is missing) # True，键不存在

成本与边界：容量前提是正整数，键必须可哈希；代码拒绝非正容量。哈希表负责查找，双向顺序结构负责移动和删除，在键哈希/比较成本视为常数、哈希分布正常时，get 和 put 通常为 O(1)，保存的条目及顺序信息占 O(capacity) 空间。容量 1 也适用；此示例没有过期时间、并发同步或按字节限制。

与 LFU 的区别：LFU（Least Frequently Used，最不经常使用）优先淘汰访问次数最低的键。若频次相同，还要约定按最近使用时间等规则打破平局；历史热点也可能需要频次衰减。LRU 看近期先后，LFU 看次数。上面只实现了 LRU，不能靠这段代码得到 LFU。

一致性哈希：新增节点，只改变一段归属

假设多个缓存节点共同保存数据。直接用“哈希值除以节点数的余数”路由时，节点数变化可能让大量键重新分配。一致性哈希把键和节点放到同一位置空间，给每个键找沿环向前遇到的第一个节点。

输入：教学空间为 [0,100)，沿数值增加方向顺时针。初始节点为 A=20、B=50、C=80，键的位置为 10、30、45、60、90。查找第一个位置不小于键位置的节点；没有时绕回第一个节点。这里的位置视为已算好的哈希结果，不把单词直接当作数值。

键位置加入 D=35 前加入 D=35 后沿环查找的理由
10A=20A=20第一个不小于 10 的节点仍是 20
30B=50D=35（迁移）35 成为第一个不小于 30 的节点
45B=50B=5035 小于 45，继续前进到 50
60C=80C=80第一个不小于 60 的节点仍是 80
90A=20A=20没有节点位置 ≥90，绕回 20

为什么只迁移这一段？D 插入 A 和 B 之间，只有位置在 (20,35] 的键会比以前更早遇到 D；其他位置遇到的第一个节点没变。左端不含 20，因为该位置仍归 A；右端包含 35，因为相等也归 D。示例中只有 30 落在这段，45 仍归 B，90 仍绕回 A。这描述的是目标归属，真正把数据搬到新节点还要由系统执行迁移。

成本与边界：若有 V 个排好序的节点位置，二分找后继节点需 O(log V)，位置表占 O(V) 空间；计算键哈希还需要读取键本身。用虚拟节点（一个真实节点占据环上的多个位置）通常能改善分布，但不保证每个节点负载相等，热点键仍需单独处理。一致性哈希负责路由，本身不提供数据复制或故障恢复。

区分 Redis Cluster：Redis Cluster 使用 16384 个哈希槽，把槽分给节点；扩容时迁移槽及其数据。它不能直接作为这里的一致性哈希环实例。Redis 官方分片说明明确区分了这两种方式。

布隆过滤器：先排除肯定没见过的名字

如果查询不存在的名字也会访问慢存储，可以先用一个很小的位数组筛一遍。Bloom filter（布隆过滤器）不保存原文，而是用若干哈希函数把每个名字映射到几个下标，插入时把对应的位设为 1。

输入：8 位数组，下标从 0 开始；使用两个简化哈希结果。初始全为 0。这里只插入 cat，两个位置是 1 和 5；dog 也得到 1 和 5，fox 得到 2 和 5。这些是为说明碰撞而指定的教学值。

查询检查下标读到的位结论与下一步
cat1、51、1可能存在；查真实存储确认。本例确实插入过。
dog1、51、1可能存在；查真实存储后发现未插入，是假阳性。
fox2、50、1位 2 为 0，肯定没有插入过，可以排除。

为什么正负结论不同？插入名字必定把它对应的所有位设为 1，所以只要遇到一个 0，就能排除“已插入”。但看到全 1 时，这些位可能由别的名字设置，例如 dog 与 cat 碰巧用了同样的下标。这叫假阳性（没插入却被报告为可能存在）。

成本与边界：用 m 位、k 个哈希位置，每次插入或查询检查 O(k) 个位，空间为 O(m) 位；哈希计算还取决于名字长度。位数组相对插入量越小、越来越多位被占满，误判通常越多，k 也需随参数选择。它适合做快速预筛，不能独自完成要求准确的去重。

“不会漏掉已插入项”有前提：这是只插入的标准布隆过滤器，插入与查询使用相同参数和哈希函数，状态未损坏且已包含需要查询的数据。不能为了删除 cat 随意把位 1 或 5 清零，因为其他名字也可能依赖这两位。需要删除时应选用专门支持删除的结构。过滤器报告“可能存在”后仍要查真实存储。

字符串：选算法前，先看模式有几个

模式是要找的字符串，文本是被搜索的内容。例如在 ababac 中找 abac，与在同一段文本中同时找一万条词语，是不同的任务。下面用 n 表示文本长度、m 表示单个模式长度、L 表示所有模式长度之和、z 表示实际输出的匹配数。

算法与问题关键动作 / 小例子成本的条件与限制
KMP（Knuth–Morris–Pratt）：找一个固定模式的出现位置。预先记录模式前缀中“同时也是后缀”的长度。搜 abac 时，前缀 aba 后本该匹配 c 却读到 b，可以把已匹配长度从 3 回退到 1，再比较 b；文本指针不用退回开头。按字符访问和比较为 O(1) 时，预处理 O(m)、扫描 O(n)、辅助空间 O(m)。适合单模式精确匹配；分词、模糊匹配不是它直接解决的问题。
Trie（字典树）：找以某个前缀开头的词。每条边代表一个字符。cat 与 car 共享 c → a，再分到 t 或 r；查询 ca 就先按字符走到 a，再枚举其后代。子边查找为 O(1) 时，长度 q 的前缀定位 O(q)，枚举结果还要付出遍历和输出成本；存储随已建的字符路径总量增长。它按前缀查找，不能直接高效搜索单词中间的任意子串。
AC 自动机（Aho–Corasick）：一次扫描查找多个固定模式。先把模式建成 Trie，再加失败链接。当前路径走不通时，失败链接找到仍可能继续匹配的后缀状态；例如匹配 she 时，也可能输出作为后缀的 he。在固定字符表或可常数时间完成转移的实现中，构建常写作 O(L)，扫描并报告结果为 O(n+z)。字符表、转移表方式影响构建时间和空间；匹配输出极多时 z 本身就很大，修改词库也可能需要重建链接。
Rabin–Karp（拉宾–卡普）：用窗口哈希筛选匹配位置。长度 m 的窗口每次右移，移除旧字符贡献并加入新字符；窗口哈希与模式哈希相等时，再核对原文，避免把碰撞当匹配。滚动更新和字符运算为常数成本、碰撞较少时，预处理与扫描通常接近 O(n+m)；核对候选需要额外时间，最坏可达 O(nm)。哈希相等不保证原文相等。

选择练习：只有一个关键词，先看 KMP；需要从 ca 补全单词，先看 Trie；大量固定词同时检索，先看 AC；希望用窗口指纹先筛候选，再看 Rabin–Karp。先核对任务条件，再比较实现成本。

B+ 树：让一次磁盘读取带来更多导航信息

数据库索引往往装不进内存，而磁盘按页读写。B+ 树让一个内部节点保存多个分隔键和多个孩子指针，一次读页便能决定下一层去哪；数据记录或记录指针放在叶子，叶子之间通常按顺序相连。

例如分隔键 20、40 把查找分成“小于 20”“20 到 40 之间”“不小于 40”三个方向（具体端点规则由实现约定）。查范围 [22,35] 时，先定位第一个不小于 22 的叶子位置，再顺着叶子往后读，到超过 35 时停止，无需每次从根重新查找。

为什么常用？每个节点能容纳很多孩子，树的高度较低，点查通常只需读少量层级；叶子的有序连接便于范围扫描。因此 B+ 树是许多数据库索引的常见结构。

成本与边界：在页式外存模型下，设有 N 条记录、有效分支数约为 b，一次点查通常需 O(logb N) 次页访问；范围查还要读取覆盖结果的叶子页并输出记录，不能把全部结果当常数成本。索引空间随 N 增长，插入和删除可能触发节点分裂、合并和页写入。真实成本还受缓存、页大小、键大小及索引是否覆盖所需字段影响；并非所有数据库索引都用 B+ 树。
